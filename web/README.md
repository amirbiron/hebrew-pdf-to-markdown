# השירות: PDF עברי ל-Markdown בדף אחד

שירות נפרד באותו ריפו: דף HTML אחד בעברית, וראוט אחד שממיר. מעלים PDF, ומקבלים את ה-Markdown כמו שהוא יועתק ויורד, ולכל עמוד החלטה (תקין, לא בטוח, נפסל), סיבות והערות. בלי מסד נתונים ובלי שמירה של שום דבר.

## הרצה

```bash
pip install -r web/requirements.txt
```

`web/requirements.txt` נועל את כל התלויות של השירות, גם את אלה שהחבילות הישירות מושכות, בגרסאות שהבדיקות רצו עליהן, ובדיקה מוודאת שהרשימה שלמה (`tests/test_web_deploy.py`).

```bash
python -m web
```

ואז `http://127.0.0.1:8000`. ברירת המחדל מאזינה רק ל-127.0.0.1; ב-Render `HOST=0.0.0.0` מוגדר ב-`render.yaml`. הבדיקות של השירות הן `tests/test_web_*.py`, והן צריכות את `requirements-dev.txt` ואת Chromium של Playwright.

## הדפים שנגישים בלי התחברות

כולם. השירות ציבורי בכוונה, ואין בו שום פעולת ניהול או כתיבה.

| נתיב | מה |
|---|---|
| `GET /` | הדף |
| `GET /static/app.js`, `style.css`, `icon.svg` | הקבצים של הדף, ותו לא (רשימה סגורה ב-`web/app.py`) |
| `GET /healthz` | בדיקת הדופק של Render |
| `POST /api/convert` | גוף הבקשה הוא הקובץ עצמו (`application/pdf`), לא טופס |

FastAPI לא מגיש `/docs`, `/redoc` ו-`/openapi.json`: אלה היו דפים ציבוריים נוספים שטוענים סקריפט ממקור חיצוני.

## מקור אחד לתוצאה

המסלול מהקריאה לתוצאה הוא `hebrew_pdf.convert.convert_pages`. מערך הבדיקה (`harness/run.py`) קורא לה ישירות עם העמודים שהקורא שלו הוציא, והשירות קורא ל-`convert_document`, שקוראת את המסמך ואז ל-`convert_pages`. `tests/test_web_identity.py` מוודא על כל 15 הקבצים שמה שחוזר מהראוט זהה תו בתו למה שמערך הבדיקה מפיק: ה-Markdown שהוא כותב ל-`output/`, וההחלטות, הסיבות וההערות שבדוח.

כדי שלחיצה על עמוד תוביל לסמן שלו בטקסט, ה-Markdown רושם בזמן הבנייה איפה מתחיל הסמן של כל עמוד (`Markdown.page_offsets`). זה לא חיפוש של המחרוזת `<!-- page N -->` אחר כך, כי טקסט מהקובץ שכתוב בו בדיוק זה יוצא אחרי ההגנה כ-`\<!-- page N -->`, וחיפוש היה מוצא אותו. לדף נשלח מספר השורה ולא המקום בתווים, כי אינדקס של תו בפייתון ובג'אווהסקריפט שונה אחרי כל אימוג'י.

## ההגנות

הסדר בראוט, מהזול ליקר, וכל שלב דוחה לפני הבא:

1. **הגבלת קצב לפי כתובת:** 30 המרות ב-10 דקות לכל כתובת. הכתובת נלקחת מ-`CF-Connecting-IP`: לפי Render, Cloudflare כותב אותה בכל בקשה לשירות ציבורי ודורס את מה שהלקוח שלח, ואילו ל-`X-Forwarded-For` הוא מוסיף ולא מחליף, כך שהכתובת הראשונה בו היא מה שהלקוח כתב ([Render, PocketBase](https://render.com/articles/host-pocketbase-on-render)). ולכן uvicorn רץ בלי `proxy_headers`: בקוד שלו, כשסומכים על כל הפרוקסים (`*`), הוא לוקח את הכתובת השמאלית ב-`X-Forwarded-For` (`uvicorn/middleware/proxy_headers.py`).
2. **דחייה זולה לפני קריאת הגוף:** בלי `Content-Length`, או עם `Transfer-Encoding` לידו, 411; מעל 10MB, 413. מהכותרות בלבד, עם `Connection: close`. הבדיקה שולחת כותרות בלי גוף בכלל ומקבלת 413 תוך פחות משתי שניות, מול בקרה שבה השרת כן מחכה לגוף.
3. **עומס:** כשכל המקומות להמרה תפוסים, 503 מיד, בעברית, עם `Retry-After`. אין תור. המקום נתפס כאן, לפני קריאת הגוף, ומשתחרר בסוף ההמרה, כך שאין קבצים בדרך מעבר למקומות, וגם קובץ שעוד נקרא תופס מקום.
4. **קריאת הגוף** עד האורך המוצהר, בתוך 60 שניות לכל הקריאה (ל-uvicorn אין מגבלה כזו), ישר לחוצץ בגודל המוצהר.
5. **סוג הקובץ לפי התוכן:** הכותרת `%PDF-` מתחילה במקום 0 עד 1024, כמו ש-PDFium מקבל (נמדד: במקום 1024 הקובץ נפתח, במקום 1025 לא).
6. **ההמרה בתהליך נפרד**, עם זמן ותקרת זיכרון. מספר העמודים נבדק מיד אחרי הפתיחה, לפני ההמרה.

**למה הקובץ נשלח כגוף הבקשה ולא כטופס:** ב-Starlette קובץ בטופס שגדול מ-1MB נכתב לקובץ זמני בדיסק (`starlette/formparsers.py`, `spool_max_size`). כאן הוא נשאר בזיכרון, ו-python-multipart לא נדרש.

### זמן שבאמת עוצר את העבודה

כל המרה רצה בתהליך חדש (`web/conversion.py`), וכשהזמן נגמר התהליך נהרג ב-SIGKILL. חוט אי אפשר לעצור מבחוץ: הפסקת ההמתנה לו (`asyncio.wait_for`) משאירה אותו רץ ואוכל מעבד וזיכרון. תהליך נהרג, ומערכת ההפעלה מחזירה את כל הזיכרון שלו, גם מה ש-PDFium הקצה. בדרך יש עוד שני רווחים: קובץ שמפיל את PDFium מפיל רק את התהליך שלו, והזיכרון של כל המרה חוזר כשהיא נגמרת. מאגר תהליכים קבוע לא מתאים: הוא לא נותן להרוג משימה אחת.

התהליכים נוצרים משרת תהליכים (`forkserver`) שמתחיל פעם אחת ומייבא מראש את pypdfium2 ואת החבילה, כך שתהליך חדש עולה מהר ולא יורש את לולאת האירועים של השרת. הבדיקה (`TimeoutStopsTheWorkTest`) רואה את התהליך של ההמרה בזמן שהיא רצה, ומוודאת שאחרי התשובה הוא כבר לא קיים.

**התקשורת עם התהליך:** שני pipes, אחד לקובץ ואחד לתשובה, שלולאת האירועים כותבת וקוראת בחלקים ובלי לחסום. כל ההחלפה (שליחת הקובץ, ההמרה וקבלת התשובה) בתוך הזמן להמרה. הקובץ לא עובר בארגומנטים של התהליך, כי שם multiprocessing כותב אותו ברצף אחד בתוך `process.start`, בתוך הלולאה. התשובה נקראת עד 4MB: קובץ PDF דחוס יכול להפוך להרבה יותר טקסט מהגודל שלו, ומעבר לתקרה התהליך נהרג. והיא JSON ולא pickle: התהליך מפענח קובץ עוין, ותהליך שהקובץ השתלט עליו היה יכול לשלוח pickle שמריץ קוד בשרת. המבנה של התשובה נבדק שדה שדה לפני שמשתמשים בו.

**תקרת זיכרון לכל המרה:** 192MB זיכרון וירטואלי (`RLIMIT_AS`). כך המרה כבדה מהצפוי נכשלת לבד, ולא מפילה את השירות. נמדד: מעבר לתקרה PDFium מפיל את התהליך (SIGABRT), ולא זורק `MemoryError`, ולכן ההודעה למשתמש היא "פגום או מורכב מדי", וקוד היציאה נרשם בלוג.

### כמה המרות במקביל: מהזיכרון ומהמעבד

הקטן משני חשבונות (`web/limits.py`, `capacity`). **הזיכרון** (`slots_for`): הזיכרון של השירות, פחות הבסיס ושוליים, חלקי מה שמקום אחד עולה. **המעבד** (`cpu_slots`): כמה המרות מכסת המעבד מספיקה לסיים בזמן להמרה, גם את האיטית בסט. הזיכרון לבדו לא מספיק: הזמן להמרה נמדד בשעון, והמרות במקביל חולקות את המעבד, כך שבחצי מעבד שתי המרות של קובץ הטבלאות היו צריכות כ-95 שניות כל אחת, ושתיהן היו נעצרות ב-90.

| | ערך | מאיפה |
|---|---|---|
| הזיכרון ב-Render | 512MB | התוכנית `0.5c-512mb` ([compute plans](https://render.com/docs/compute-plans)) |
| הבסיס | 100MB | השרת 56.2, שרת התהליכים 28.0, resource_tracker 14.6 (שיא פיזי, אחרי המרה של הדוח הכספי) |
| שוליים | 64MB | מה שלא נספר לכל מקום: חיבורים, הלוג, הפיצול של הזיכרון בפייתון |
| מקום אחד | 194MB | תהליך ההמרה 164 (התקרה הווירטואלית 192 פחות כ-28MB שלא מגיעים לזיכרון), הקובץ אצל השרת 10, והטיפול בתשובה 20 (פי 5 מהתשובה הגדולה שמותרת, 4MB; נמדד פי 4.9) |
| לפי הזיכרון | 1 | (512 − 100 − 64) / 194 = 1.8 |
| המעבד ב-Render | 0.5 | אותה תוכנית |
| זמן המעבד של ההמרה האיטית | 23.6 שניות | קובץ הטבלאות, `python -m web.measure` |
| לפי המעבד | 1 | 0.5 × 90 / 23.6 = 1.9 |
| **המרות במקביל** | **1** | הקטן מהשניים |

השירות קורא את שתי המגבלות מ-cgroup בזמן ריצה (`memory.max` ו-`cpu.max`, או המקבילים ב-v1). כשמגבלת הזיכרון לא ידועה הוא יורד להמרה אחת ורושם את זה, ולכן המספר כתוב גם ב-`render.yaml` (`HEBREW_PDF_SLOTS=1`), ובדיקה מוודאת שהוא שווה לחישוב. שורת הלוג בעלייה אומרת כמה מקומות הותקנו ולמה. עובד אחד של uvicorn, בכוונה: ההמרות כבר בתהליכים נפרדים, והמגבלות נספרות בזיכרון של התהליך. החשבון של המעבד מניח שליבה ב-Render מהירה כמו המכונה שבה נמדד, וזה לא נבדק.

### הדף

- **CSP:** `default-src 'none'`, וסקריפט, סגנון, אייקון ו-fetch רק מהשירות עצמו. אין בדף סקריפט או סגנון מוטמע. הבדיקה בדפדפן סופרת הפרות CSP (אפס), ומוטציה שמוסיפה `style=` אחד נכשלת בה.
- **הכול נכנס כטקסט:** ה-Markdown, השמות, הסיבות וההודעות נכנסים ב-`textContent`. אין `innerHTML` בקובץ.
- **הכיוון:** אזור הפלט ב-`dir="rtl"`, ובכוונה בלי `unicode-bidi: plaintext`: כל שורה מוצגת בפסקה עברית, כי זה מה שבדיקת התצוגה של הקורא מאשרת. גם זה נבדק בדפדפן, עם מוטציה.
- **העתקה והורדה** של המחרוזת עצמה, ולא של הטקסט שבדף. שם ההורדה נגזר בדף משם הקובץ שהועלה (בלי תווי בקרה ותווי כיוון, בלי תווים אסורים בשם קובץ, עד 120 תווים), והשם לא נשלח לשרת בכלל.
- **פרטיות:** הקובץ לא נשמר, ובלוג אין שום דבר ממנו. חריגה בתהליך ההמרה נרשמת כסוג ומיקום בקוד בלבד, בלי ההודעה שלה, כי הודעה יכולה להכיל טקסט מהקובץ.
